# IT Support — course access triage

Read [shared scope](README.md). Objective: distinguish a legitimate missing-access case, correct denial and suspected unauthorized access, using the existing server-issued tickets workflow.

1. Retrieve only your current assigned-pod tickets. Verify synthetic identity using mentor-approved synthetic attributes; never request real identity documents or credentials.
2. Record the reported symptom and chronology. Read authorized account/course enrolment/ownership evidence with minimum necessary fields; keep facts separate from hypotheses.
3. Decide whether denial matches policy. A request for another learner's private assignment is not automatically an authorized ownership transfer.
4. Escalate unexpected successful access as a possible security incident, preserving safe evidence IDs and actor/resource context without pre-deciding root cause.
5. For a legitimate correction, submit the existing approved change request and record the authorized mentor/operator decision. Do not grant access through local flags or platform entitlement changes. If bounded server-side correction is not published, document a proposed or simulated resolution only.
6. Record authorized before/after course state and a reproducible recovery check, or mark verification pending. Preserve evidence and a rollback/escalation plan; write a short knowledge-base note.

Submit `ticket-resolution.md` using [the template](templates/ticket-resolution.md), a safe chronology and evidence register. Do not modify accounts, roles or shared data without the required approval.
